# LightKV 缺陷修复方案

> 基于对 `main` 分支 HEAD（commit `5d563e7`）的逐行核实、实际构建与测试。
> 文档中所有结论均标注了 `文件:行号`，可直接定位复核。
>
> 核实环境：Windows / Clang 22.1.0 (MSVC ABI) / Ninja / Release + `/UNDEBUG`（测试）
>
> **修订说明**：初版曾记录「Windows 上 14 个测试中 10 个失败」，该结论**已被证伪**——
> 失败来自本机安全软件对特定可执行文件的按文件拦截，而非代码缺陷。详见 §1.1。
> 现版本记录的是修复后的真实基线与已验证的缺陷。

---

## 一、基线核实结果

### 1.1 一个必须先排除的环境陷阱

在 `D:\lightkv\build\tests\` 下直接运行测试，最初观察到 10/14 失败：

```
WALTest(SEGFAULT)  SSTableTest(0xc0000409)  DBTest(SEGFAULT)
ServerTest P0Test P1Test P2Test ZSetTest GeoTest AuthTest
  (Failed: "cannot open WAL file")
```

排查过程与结论：

| 证据 | 结论 |
|---|---|
| 错误为 `errno=13` / `CreateFileA` 返回 `winerr=5 (ACCESS_DENIED)` | Win32 层拒绝，非权限/路径问题 |
| 路径字节逐字节 dump 完全正常（38 字节纯 ASCII） | 排除隐藏字符 |
| 用相同编译器、相同编译选项的独立探针程序打开**同一路径** | **成功** |
| 把 `p0_test.exe` 原样复制到 `%TEMP%` 再运行 | **66/66 测试通过，退出码 0** |

**结论：本机安全软件（Defender 等）按可执行文件拦截了 `D:\lightkv\build\tests\*.exe`。**

**因此：任何从 `build/` 目录直接得出的测试结论都不可信。**
正确做法是把测试二进制复制到 `%TEMP%` 后运行，或在 CI 的干净环境运行。

> 这一点对后续所有验证都成立，本文档中的所有测试结果均按上述方式取得。

### 1.2 真正的问题：Release 构建下测试是空跑

排查过程中发现的**根本性**问题（与 §1.1 无关）：

`tests/db_test.cpp`、`tests/memtable_test.cpp` 等全部使用裸 `assert()` 做正确性断言，
而默认构建为 Release，编译选项含 `-DNDEBUG`（`CMakeLists.txt:14,24`）。

**默认构建下所有正确性断言被编译掉，测试「通过」不代表功能正确。**

关闭 NDEBUG 后立即暴露 4 个真实缺陷（见 §二），其中 2 个是数据丢失级。

## 二、已修复的缺陷

### F-1　MANIFEST 静默不更新 → 重启后丢数据 【已修复】

**严重度：最高（数据丢失）**

8 处文件打开**全部缺少 `O_BINARY`**：

```
src/manifest.cpp:49,87,100   src/sstable.cpp:42
src/wal.cpp:18,262           src/vlog.cpp:27      src/table_builder.cpp:18
```

Windows 上不加 `O_BINARY` 即为**文本模式**，CRT 会把每个 `\n` 写成 `\r\n`。
于是 `Manifest::WriteToFile` 中（`src/manifest.cpp:71-78`）：

```cpp
ssize_t written = ::write(fd, content.data(), content.size());
...
if (static_cast<size_t>(written) != content.size()) {
    ::unlink(tmp_path.c_str());
    return Status::IOError("failed to write MANIFEST");
}
```

`written` 因 CRLF 膨胀而大于 `content.size()` → **返回错误**；
而 `DBImpl::UpdateManifest()`（`src/db_impl.cpp`）**丢弃了返回值** → 静默失败。

**后果**：MANIFEST 永远停留在旧状态（`next_file_id` 不前进、SSTable 不登记）。
重启后 `Initialize()` 按旧 MANIFEST 加载，重启期间写入的数据对应的 SSTable 不被识别 → **数据丢失**。

复现：`TestMultipleReopen` 在第 2 轮丢失第 1 轮全部数据
（`round=2 key=r1_000 Get failed: NotFound`），磁盘上 `2.sst` 存在但 MANIFEST 只登记了 `1.sst`。

**修复**：
- 8 处打开全部加 `| O_BINARY`（POSIX 下为 `0`，无副作用）
- `UpdateManifest()` 不再吞掉错误，失败时打印 FATAL 并说明后果

### F-2　`platform_rename` 未实现替换语义 → MANIFEST 永不更新 【已修复】

POSIX `rename()` 会**原子替换**已存在的目标；MSVC CRT 的 `rename()` 在目标存在时
返回 `EEXIST`（实测 `errno=17 File exists`）。

`platform.h` 里原封不动地包了一层 `rename()`，等于是个假的 POSIX 语义垫片。

**修复**：Windows 下改用 `MoveFileExA(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`，
并把常见 Win32 错误码映射回 errno。

### F-3　压缩后读到旧值（P0-1 的真实根因在读路径）【已修复】

**严重度：最高（静默返回陈旧数据）**

原判断「SSTable 不持久化 seq 导致压缩随机丢数据」**方向正确但根因定位有误**。
实际首先失效的是**读路径**：

`DBImpl::Get`（`src/db_impl.cpp:355-365`）按 `levels_[0]` **向量顺序**扫描并返回首个命中。
`levels_[0]` 由 `WriteLevel0Table` 用 `push_back` 追加（`src/db_impl.cpp:622`），
即**索引 0 是最旧的文件**。因此只要 key 还留在某个旧 L0 文件里，
**旧值就会赢过新值**——与压缩是否发生无关。

复现（`tests/db_test.cpp: TestCompactionKeepsNewestVersion`）：
每轮覆写 16 个 key 并强制 flush/压缩，**每轮压缩后立即校验**：

```
compaction lost the newest version at round=4 key=contended_0:
  Get -> OK, value='round_1', expected='round_4'
```

3 次运行结果完全一致（确定性，非随机 tie-break）——旧值稳定胜出，
这正是「读路径最旧优先」的特征，而非堆排序不确定性。

**修复**（三处，全部基于单调的 `file_id` 作为「新旧」信号）：
1. `DBImpl::Get`：**逆序**扫描 `levels_[0]`（新 → 旧）。顺带让墓碑语义正确：
   新文件中的删除可以遮蔽旧文件中的值。
2. `src/compaction.cpp`：合并堆比较器增加 `file_number` tie-break
   （`key ASC → seq DESC → file_number DESC`）。
3. `src/iterator.cpp`：`SourceIterator` 增加 `recency()`，
   MemTable 返回 `INT64_MAX`，SSTable 返回 `file_id()`；
   `MergingIterator::Compare` 用它做 seq 相等时的 tie-break（SCAN 路径）。

修复后连续 3 轮测试稳定通过，且 Get 与 SCAN 两条路径都覆盖。

> **仍然遗留的问题**（Phase 1b）：SSTable 依旧不持久化 seq。
> 上述修复是用「文件新旧」近似「版本新旧」，
> 因此**压缩期间持有旧快照的读者仍会读到错误数据**。
> `src/compaction.cpp:160` 的快照判断 `entry.seq <= oldest_snapshot_`
> 因 `seq` 恒为 0 而永远为真，无法真正表达快照可见性。

### F-4　`WALWriter::Truncate()` 在 mmap 存活时截断 【已修复】

**严重度：中（WAL 截断失败）**

`Truncate()` 先 `ftruncate` 后 `platform_munmap`。Windows 上 `_chsize`
（`SetEndOfFile`）在文件仍有活动映射时失败，实测 `errno=13 EACCES`
（`ERROR_USER_MAPPED_FILE`）。POSIX `ftruncate` 无此限制，所以只在 Windows 暴露。

**修复**：先 munmap，再截断，再重新映射；`write_pos_ == 0` 时保留一个块的映射。

### F-5　`platform_mmap` 失败返回值与 `MAP_FAILED` 不一致 【已修复】

**严重度：中（错误被静默吞掉）**

Windows 上 `MAP_FAILED` 定义为 `((void*)-1)`（`platform.h`），
但 `platform_mmap` 失败时返回 **`nullptr`**。
于是全代码库所有 `if (x == MAP_FAILED)` 检查在 Windows 上**永远为假**——
mmap 失败会被当作成功，随后解引用空指针。

**修复**：Windows 下 `platform_mmap` 统一返回 `MAP_FAILED`，
并把 `MAP_FAILED` 的定义前移到 `platform_mmap` 之前。

### F-6　`DBImpl::Initialize` 静默吞掉目录创建失败 【已修复】

`create_directories` 的错误码被忽略，后续以完全无关的
「cannot open WAL file」形式在另一层报错，极难定位。
**修复**：创建后显式 `is_directory` 校验，失败时返回可读的错误信息。

### F-7　`platform.h` 使用 `int64_t` 但未包含 `<cstdint>` 【已修复】

`platform.h:131,145` 使用 `int64_t`。仅因其他头文件恰好先引入了 `<cstdint>`
才能编译通过——独立包含 `platform.h` 会直接编译失败。

**修复**：在 `platform.h` 顶部显式包含 `<cstdint>` / `<cstddef>`。

### F-8　测试依赖已存在的临时目录 【已修复】

`wal_test` / `sstable_test` 直接在 `LIGHTKV_TEST_TMP` 下 `unlink`/打开文件，
从不创建该目录。干净机器上必然失败。

**修复**：`test_paths.h` 增加进程启动时自动创建临时根目录。

### F-9　测试断言失败无诊断信息 【已修复】

`assert(s.ok())` 失败时不打印 `Status`，无法定位。
已在 `wal_test`（WAL truncate）与 `db_test`（reopen、newest-wins）中补充失败上下文输出。

### F-13　集群模式下不可复制的写命令被静默执行 → 副本发散 【已修复】

**严重度：高（集群数据不一致，无任何报错）**

在 `--cluster` 模式下只有 `SET` 与 `DEL` 走 Raft 复制；
其余写命令（`HMSET`/`LPUSH`/`ZADD`/`INCR`/`SADD`/`DELRANGE`/`EXPIRE` …）
直接改本地库，而 follower 的 `RaftDBAdapter::Apply` 只认 `SET`/`DEL`，其余静默丢弃。

**后果**：任意一次非 string 写操作都会让各节点状态发散，且**不产生任何日志**。

更糟的是，连唯一「声称支持 Raft」的 `SET` 也不完整：
`handle_set` 的 Raft 分支把 **TTL 元数据直接写本地库**（TTL 是第二个 key），
所以 `SET k v EX 100` 会让每个节点对过期时间产生分歧。

**修复**：在**命令分发层**（worker-pool 与 inline 两条路径都加了）加写入闸门：

- 非集群模式：全部放行
- 集群模式 + 只读命令：放行
- 集群模式 + `SET`/`DEL`：放行（handler 内部走 `raft_write`）
- 集群模式 + 其他写命令：**显式拒绝**
  - 非 leader → `READONLY You can't write against a read only replica`
  - leader → `ERR <CMD> is not supported in cluster mode: ...`
- `SET` 带 `EX/PX/EXAT/PXAT`：显式拒绝（TTL key 无法原子复制）

这把「数据静默发散」变成了「功能明确受限」。新增 `tests/cluster_test.cpp`，
用单节点集群做端到端验证（35 项断言，含 20 个必须被拒绝的命令、
读命令不受影响、被拒命令确实没有落到本地 DB）。

### F-14　单节点 Raft 集群永远无法当选 leader 【已修复】

**严重度：高（`--cluster` 单节点部署完全不可用）**

`StartElection()` 先 `votes = 1`（自投票），随后遍历 `opts_.peers` 发送
RequestVote——但循环里 `if (peers[i].id == opts_.node_id) continue;`
**跳过了自己**，于是循环体一次都不执行；
而 `BecomeLeader()` 只在循环**内部**被调用。

结果：单节点集群永远反复 campaign，永远当不上 leader。

**修复**：循环结束后补一次计票判断。

### F-15　Raft 提交阈值把 leader 自己数了两遍 → 从不提交 【已修复】

**严重度：极高（Raft 共识实质失效）**

`AdvanceCommitIndex()` 中：

```cpp
uint64_t replicated_count = 1;   // leader 自己
...
uint64_t voters = 1;                          // ← leader 又被算一次
for (const auto& peer : opts_.peers) {
    if (peer.is_voter) voters++;              // ← 这次循环不跳过自己
}
uint64_t majority = voters / 2 + 1;
```

- **单节点**：`voters = 2`、`majority = 2`，但只有 1 个副本 → `1 >= 2` 为假 →
  **永远不提交**（`commit_index_` 恒为 0）
- **三节点**：`voters = 4`、`majority = 3` → 要求**全票一致**才提交，
  Raft 的多数派提交被写成了全等，容错能力完全丧失

实测：`Propose()` 成功（日志 2→3），300ms 后 `commit_index` 仍为 0；
每次 `ProposeSync()` 卡满 5 秒超时后返回失败。

**修复**：voters 只统计一次 peer 列表中的投票节点，本节点不在列表时再补 1。

> 这一条与 F-14 叠加，意味着 **Raft 在任何配置下都无法完成一次多数派提交**。
> 该实现此前从未被端到端验证过（`--cluster` 路径零测试覆盖）。

### F-16　`ProposeSync()` 等待时用错互斥量 → 丢唤醒 + 每次卡满超时 【已修复】

**严重度：高（每次同步写阻塞 5 秒后误报失败）**

`ProposeSync()` 用 `commit_mu_` 等待 `commit_cv_`，但：

- `commit_index_` 由 `mu_` 保护
- `commit_cv_.notify_all()` 是在持有 `mu_` 时调用的
- `commit_mu_` **只**在这一处出现，不保护任何数据

两者之间没有 happens-before 边，等待方可能永远看不到 `commit_index_` 的更新，
只能等超时后重新求值并返回 `false`。

**修复**：改为使用 `mu_` 等待，并删除无用的 `commit_mu_` 成员。

### F-17　`Server::Stop()` 返回后 TTL / worker 线程仍在读写 DB → use-after-free 【已修复】

**严重度：高（退出期偶发崩溃，约 1/14 概率复现 `0xC0000005`）**

`ttl_running_` 只在 `~Impl()` 里被清零，`ThreadPool` 的停止也只在析构里。
因此 `Stop()` 返回后：

- TTL 线程仍在每秒调用 `db_->Get` / `db_->Delete`
- worker 池线程仍可能执行命令 handler

而 `Server` 是栈对象，其析构发生在 `delete db` **之后**
（`delete db; ...; return 0;` → 栈上的 `server` 才析构）。
任何「先停服务再释放 DB」的宿主写法都会与后台线程竞争。

**修复**：把 TTL 线程与 worker 池的停止/join 移入 `Server::Stop()`，
使其成为幂等的「返回即安全」操作；析构只做兜底。

**测试验证**：`cluster_test` 退出码崩溃从 ~1/14 降为 12/12 无复现。

### F-10　Raft 伪造快照占位 + 自动日志压缩 → 集群数据丢失 【已修复】

**严重度：高（集群模式下不可恢复的数据丢失）**

- `src/raft.cpp` `TriggerSnapshot()`：状态机返回空快照时，
  **伪造**一个 `"snapshot_at_" + index` 占位串，然后照常调用 `CompactLog()`
- `tools/server_main.cpp:210-218`　`TakeSnapshot()` 直接 `return ""`，`ApplySnapshot()` 空实现
- `include/lightkv/raft.h`　`snapshot_threshold_ = 10000`，日志超限**自动触发**

**失效链条**：日志超 10000 条 → 自动快照 → 占位串 → `CompactLog()` 永久删除
1..snap_index 的全部日志 → 落后 follower 收到占位串 → 真实状态已被删除，**无法恢复**。

**修复**：
1. **删除伪造占位逻辑**。状态机给不出真实快照时 `TriggerSnapshot()` 返回 `false`
   并记录日志，**绝不压缩日志**。
   —— 日志无限增长远比静默数据发散可接受；集群保持正确性。
2. `HandleInstallSnapshot()` **拒收空负载**：否则会截断 follower 的日志
   却不替换其状态，比落后更糟。
3. 新增 `tests/raft_test.cpp`（此前 Raft **完全没有测试覆盖**），三个用例：
   - 状态机无法快照 → `TriggerSnapshot()` 失败且日志长度不变
   - 状态机正常 → 快照成功且日志被压缩（确认没有把正常路径一起禁用）
   - 空 `InstallSnapshot` → 被拒绝且日志不变

> **仍然遗留**：`RaftDBAdapter` 的 `TakeSnapshot()`/`ApplySnapshot()` 仍是空实现，
> 因此**当前集群永远不会压缩日志**（leader 内存/磁盘持续增长）。
> 另外 `src/raft.cpp` 中「如果日志落后太多，使用安装快照」处的注释表明
> 落后 follower 的补齐路径也未实现——由于不再压缩日志，follower 可通过日志复制
> 恢复，因此集群是**正确但低效**的。这一项需要 Phase 2.3 补齐。

### F-11　Raft RPC 结构体存在未初始化成员 【已修复】

`AppendEntriesRequest`、`RequestVoteRequest`、`InstallSnapshotRequest` 等
**全部标量字段都没有默认成员初始化**。这些结构体跨网络边界，且在多处被默认构造。

实测后果：`AppendEntriesRequest req;` 会让 `prev_log_index` 保持不定值，
随后在 prev-log 一致性检查处被拒绝——这是编写 raft 测试时首先撞上的问题。
生产路径上，任何未显式赋值的字段都会带着垃圾值进入 RPC 编解码。

**修复**：为所有 Raft 传输结构体与 `RaftLogEntry`/`RaftPeer` 补上默认成员初始化。

### F-12　快照读隐式返回错误结果 【已修复】

**严重度：中（公共 API 静默返回错误数据）**

`ReadOptions::snapshot_seq` 是公共字段，但 SSTable 不持久化 seq，
因此**已落盘的 key 无法定位到对应快照的版本**。
实测（`tests/db_test.cpp: TestSnapshotReadIsolation`）：

```
snapshot read FAILED: Get -> OK, value='v2', expected 'v1'
```

即**请求旧快照却静默返回最新值**，没有任何报错。

**影响面核查**（重要）：
- `DB` 没有 `BeginTransaction()`，`Transaction` 在 src/tools/tests 中**从未被构造**，
  全部 SDK 也不暴露快照读
- 即：MVCC 快照 API 目前**没有任何公共入口**

**修复（本次为「止血 + 明确边界」，非实现快照读）**：
`DBImpl::Get` / `Scan` 对非零 `snapshot_seq` 返回 `Status::NotSupported` 并说明原因，
把「静默错误结果」变成「显式报错」；`ReadOptions::snapshot_seq` 补充注释说明限制。
真正实现仍需 Phase 1b（internal key）。

### 测试基础设施（Phase 0.4 / 0.5，已完成）

### Phase 1b　SSTable 持久化 seq（已完成）

SSTable 现在按 LevelDB 式 internal key 存储：

```
internal_key = user_key || trailer(8 字节大端)
trailer = ~( (seq << 8) | type )
type: kTypeDeletion = 0, kTypeValue = 1
```

**关键设计教训：必须使用显式 comparator，不能依赖裸字节序。**

最初的设计假设「反转 trailer + 大端」能让字节序天然等于
`(user_key 升序, seq 降序)`。**这是错的。** 当一个 user key 是另一个的前缀时
（`key1` 与 `key10`），trailer 字节会参与比较并颠倒顺序：

```
"key1" 字典序 < "key10"
但 "key1"||0xFF… > "key10"||0xFF…     （第 5 字节：'0'(0x30) < 0xFF）
```

按字节序写入的文件因此**不是有序的**，`Block::Seek` 的二分查找直接失效——
表现为「`Get(key1)` 在文件明明含有该 key 时返回 NotFound」，
且只在前缀重叠的 key 上出现（`key0/key1/key10/...`）。

这正是 LevelDB 使用 `InternalKeyComparator` 而不是 `memcmp` 的原因。
现已改为显式 `CompareInternalKeys()`，并在以下位置全部替换：

| 位置 | 说明 |
|---|---|
| `src/block.cpp` `Block::Iterator::Seek` | 二分查找 + 前向扫描 |
| `src/sstable.cpp` `SSTable::Iterator::Seek` | 前一 block 的边界判定 |
| `src/db_impl.cpp` `WriteLevel0Table` | flush 时的排序 |
| `src/table_builder.cpp` | `paranoid_checks` 下的顺序校验 |

#### 其余改动

| 组件 | 改动 |
|---|---|
| `encoding.h` | 新增 internal key 编解码 + `CompareInternalKeys` |
| `TableBuilder::Add` | 签名改为 `(user_key, value, seq, type)`；Bloom 仍按 **user key** 填充 |
| `SSTable::Get` | 签名改为 `(user_key, snapshot_seq, value, &seq, &type)`；可见删除返回 OK + `kTypeDeletion`，让调用方能跨文件比较 seq |
| `SSTable::Iterator` | `key()` 返回 user key，新增 `internal_key()` / `seq()` / `type()` |
| `DBImpl::Get` | 跨重叠 L0 文件按 **seq 最大的版本**取胜者（不再是「首个命中」） |
| `DBImpl::WriteLevel0Table` | 显式排序，不再依赖跳表的隐式 LIFO 契约 |
| `MergingIterator` | 真实 seq + 删除类型；新增 `SkipInvisible()`，让快照读能回退到更旧的可见版本 |
| Compaction | 真实 seq 排序；版本保留依据 `oldest_snapshot_` 判断 |
| footer magic | `LIGHTKV1` → `LIGHTKV2`，旧文件**明确报错**并提示重建 |
| `TableBuilder` | `paranoid_checks` 下检测乱序写入并中止（此前静默接受，直接产出错读） |
| `ReadOptions::snapshot_seq` | 解除 `NotSupported`，注释说明「含端点」语义与 `LastSeq()-1` 取法 |

### P0-3　Raft 写入路径扩展（已完成）

复制的不再是「单 op + 单 key + 单 value」，而是**完整 argv**：

`
[n_args:4][len0:4][arg0][len1:4][arg1]...
`

leader 把命令交给 Raft::ProposeSync，**本节点的 apply 结果**作为响应回传给客户端
（RaftStateMachine::Apply 新增 std::string* result 出参）。
这样 leader 与 follower 走的是**同一份 handler 代码**，不存在「预计算结果再复制」
带来的语义漂移；也不会因为 leader 重复执行而产生第二次副作用。

#### 确定性约束

状态机必须是确定性的，否则各节点静默发散。两道闸门：

1. is_non_deterministic_command() —— 排除读取墙上时钟（EXPIRE/PEXPIRE/
   EXPIREAT/SETEX/PSETEX/GETEX）与使用随机数（SPOP/SRANDMEMBER）的命令。
2. aft_write_guard() 逐参数检查 —— SET k v EX 100 的命令名是 SET（在白名单里），
   但 TTL 元数据是**由墙上时钟推导出的第二个 key**，各节点算出的过期时间必然不同，
   因此按参数拒绝。

重入防护：g_applying_command（thread_local）在 apply 线程执行已提交命令时置位，
闸门与分发路径据此**直接执行**而不是再次提案，否则会无限递归。

#### 已接入复制的命令（29 个）

string（SET/SETNX/GETSET/APPEND/MSET/INCR/DECR/INCRBY/DECRBY/INCRBYFLOAT）、
keyspace（DEL/DELRANGE/RENAME/RENAMENX）、hash（HSET/HMSET/HDEL/HINCRBY/HSETNX）、
list（LPUSH/RPUSH/LPOP/RPOP/LSET/LREM/LTRIM）、set（SADD/SREM/SMOVE）、
bitmap（SETBIT）、zset（ZADD/ZREM）、geo（GEOADD）。

其余写命令仍显式拒绝，并按原因给出不同错误（未接入复制 / 非确定性）。

#### 测试

cluster_test 从 35 项扩到 **69 项**：
- 29 个已复制命令：精确校验返回的 RESP（含 HMSET 返回 +OK、INCRBYFLOAT
  返回 bulk string、LPOP 返回元素值等 Redis 语义细节）
- 25 个必须拒绝的命令，按拒绝原因分组
- 复制后的写入**确实落到状态机**（直接查 DB 的 \x02_hash_chh:a）
- 数据层面失败的已复制命令，**回传 apply 自己的错误**，而不是被静默重试

### F-18　DELRANGE / INCRBYFLOAT 语义偏差 【已修复】

- `DELRANGE` 恒返回 1：引擎不回传删除数量，与 Redis 语义不符
  → `DB::DeleteRange` 新增 `int64_t* deleted` 出参，由引擎**用自己的迭代器**
    精确统计被遮蔽的活跃 key；`handle_delrange()` 返回该计数
- `Client::DeleteRange` 硬编码 `parse_resp(resp) == "1"` —— 只在引擎恒返回 1
  的旧行为下碰巧成立，改为解析整数
- `INCRBYFLOAT` 用 `std::to_string` 输出 6 位小数（`4.000000`），Redis 返回 `4`
  → 新增 `format_double_shortest()`：以 `%.*g` 逐步加精度（1..17）取**能往返的
    最短表示**（`4` / `4.5` / `0.1`），并补上非有限结果（NaN/Inf）与非法参数校验

**新测试**：`cluster_test` 断言 `DELRANGE` 返回 `:2` / `:0`、`INCRBYFLOAT`
返回 `$1\r\n4\r\n`；`db_test: TestDeleteRangeReportsCount` 断言引擎计数与
"墓碑后重写可被再次删除"。

### F-19　range tombstone 遮蔽其后写入的 key 【已修复】

**严重度：高（`DELRANGE` 之后该 key 区间被永久封锁）**

原 `MemTable::IsRangeDeleted` 只判断「墓碑是否覆盖该 key」，**不比较 seq**：

```
DELRANGE a z      # 建立墓碑 [a,z)
SET k0 v          # seq 更大，但仍落在 [a,z) 内
GET k0            # → NotFound，写入被静默吞掉
```

这是 F-18 计数为 0 时暴露出来的**更深层缺陷**——不是计数写错，而是墓碑语义错。

**修正为「墓碑只遮蔽比自身更旧的版本」**：

- `MemTable::IsRangeDeleted(key, version_seq)` 增加 seq 比较
- `MemTable::Get` 先定位快照内最新版本，再用该版本的 seq 判断墓碑
- `MergingIterator::RangeTombstone` 增加 `seq` 字段；SSTable 墓碑从 internal key
  取 seq，内存墓碑由 `MemTable::GetRangeTombstones()` 提供

**顺带修复**：`MergingIterator` 此前**只**从 SSTable 收集 range tombstone，
MemTable 里的内存墓碑对迭代器不可见 —— 导致 `SCAN` 仍会返回已被 `DELRANGE`
删除的 key。现已在 `SeekToFirst()` / `Seek()` 两条路径注入内存墓碑。

未复制命令现在会被**显式拒绝**，集群不再静默发散。
但这意味着 `--cluster` 模式下目前**只有 `SET` 与 `DEL` 可用**。

**扩展方向**：
1. `encode_write_op()` 目前只能表达「单 op + 单 key + 单 value」，
   需要扩展为「op + 任意参数列表」的通用编码
2. `RaftDBAdapter::Apply` 需要能把通用命令派发回 server 的 handler
3. **确定性约束**：状态机必须是确定性的。凡是读取墙上时钟
   （`EXPIRE`/`SETEX`/TTL 过期扫描）或使用随机数（`SPOP`/`SRANDMEMBER`）
   或依赖返回顺序的 handler，直接复用会产生节点间分歧。
   这类命令需要改为「在 leader 求值后把结果作为命令的一部分复制」。

### F-20　Raft 状态在 Windows 上「只存第一次」 【已修复】

**严重度：高（持久化形同虚设）**

`SavePersistentState()` 用「写 `.tmp` + `std::rename()`」做原子替换。MSVC 的
`rename()` 在**目标已存在**时返回 `EEXIST`——这正是 F-2 为 MANIFEST 引入
`platform_rename()` 的原因，但 Raft 这里漏了。

后果：**第一次落盘之后，所有后续写入全部被静默丢弃**。`term` 增长、投票记录、
日志内容统统不落盘。重启后节点回到第一次保存的状态：
`voted_for_` 归零 → 同一 term 内可以重复投票 → **违反 Raft 选举安全**。

该路径此前从未被测试覆盖，因为没有任何测试重启过 Raft 节点。

**修复**：改用 `platform_rename()`；`SaveSnapshotData()` 同样处理。

### F-21　重启后日志索引整体错位一位 【已修复】

`SavePersistentState()` 写的是 `log_.size()` 条（含 index-0 dummy），
`LoadPersistentState()` 却先 push 一个 dummy 再加载 `log_count` 条。
重启后 `log_` 多出一条 dummy，**`log_[i]` 不再等于「索引 i 的条目」**，
所有按绝对索引寻址的读取（`HandleAppendEntries` 的冲突截断、
`GetTermForIndex`、`AdvanceCommitIndex`）全部错位一格。

**修复**：不再无条件补 dummy；改为按末条条目推导基址（见 F-22），
并在条目间距不一致时报 Corruption 并降级为空日志。

### F-22　日志压缩后 `log_[i]` 不再等于绝对索引 【已修复】

`CompactLog()` 直接丢弃快照点之前的条目并把其余条目前移，于是
`log_[i] <-> 绝对索引 i` 这个全局不变式被破坏。而 `GetLastLogIndex()`
返回的是 `log_.size()-1`，压缩后会变成**位置**而非真实末条索引，
`Propose()` 随即会用重复的索引追加日志。

原代码之所以「看起来能用」，是因为压缩路径从未被执行过
（`CheckAndCompactLog()` 全仓无人调用）。

**修复**：引入显式基址 `log_base_`，不变式改为
`log_[i] 持有绝对索引 log_base_ + i`：

| 位置 | 改动 |
|---|---|
| `LogPos()` / `LastLogIndex()` | 绝对索引 ↔ 位置的换算集中到两个 helper |
| `CompactLog()` | 只保留基址条目，`log_base_ = snap_index`，真正释放内存 |
| `HandleInstallSnapshot` | 日志替换为单个基址条目（不再按 `cut_index+1` 物化） |
| `AdvanceCommitIndex` / `ApplyCommitted` | 基址以下视为已由快照取代，跳过而非误读 |
| `LoadPersistentState` | 由末条条目推导 `log_base_`，**旧格式文件自动推导为 0**（向后兼容） |
| `LiveLogSize()` | 压缩阈值与 `Stats::log_count` 改用真实存活条目数 |

### F-24　`DBImpl::Backup()` 产出的不是可还原的备份 【已修复】

**严重度：高（备份静默丢数据）**

`Backup()` 在全仓**零测试覆盖**（`tests/` 下 grep `Backup` 0 命中），
`handle_backup()`（`src/server.cpp`）也只是 `static_cast<DBImpl*>(db_)` 之后
返回一句写死的 JSON，从未真正调用。逐条审查发现四个独立缺陷：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 不刷 memtable，靠 WAL 兜底；而拷贝的是整个 `wal.log`——一个 64MB 预分配 mmap 文件，尾部是未初始化填充，且**从未 `Sync()`** | 尚在 memtable 的写入可能丢失；每次备份凭空多出 64MB |
| 2 | **完全不拷 `vlog-{id}.log`** | 大 value（> `value_threshold`，默认 64KB）在 SSTable 里只有 `(file_id, offset, length)` 指针，指针指向的文件不在备份里 → 含大 value 的库备份**必然不可读** |
| 3 | 持 `shared_lock` 拷 SSTable，却**在锁外读写 manifest** | 并发压缩可能新增文件（manifest 记了、拷贝没做）或删掉文件（manifest 记了、文件已没了） |
| 4 | 直接写目标目录 | 中途失败会留下半成品备份，并覆盖掉原本完好的那一份 |

**修复**（`src/db_impl.cpp` + `include/lightkv/memtable.h` + `include/lightkv/vlog.h`）：

- 新增 `MemTable::MaxSeq()`：记录已插入的最高 seq（含点删除与 range 墓碑）。
  这就是**刷盘边界**——memtable 落成 SSTable 后，`≤ MaxSeq()` 的数据在磁盘上，
  `> MaxSeq()` 的不在
- `WriteLevel0Table()` 把边界写进 `manifest_.flushed_seq`（该字段此前是
  **从未被赋值的死字段**）与新增的 `DBImpl::flushed_seq_`
- 新增 `DBImpl::FlushForBackup()`：触发刷盘并阻塞等待 `has_imm_` 落地；
  `FlushMemTable()` 吞掉了 `WriteLevel0Table` 的错误，所以还要校验
  `flushed_seq_` 确实推进了，否则宁可报错也不返回一个缺了已确认写入的备份
- 拷贝全程持 `rw_mutex_` **独占**锁，堵住压缩与文件清理
- 拷贝 vlog 前先 `VLogManager::Sync()`（`Append` 走 mmap 写入，
  否则读到的是尚未落盘的尾部）
- 备份**不再携带 WAL**：`DB::Open` 会新建，seq 边界取自 manifest
- manifest 的 `last_seq` 填**刷盘边界**而非实时计数器。实时计数器会跑到
  边界前面，用它会让还原后的 DB 从已分配过的 seq 上继续分配，**重用 seq**
- 先写 `<path>.tmp` 再整体换入。Windows 无法 rename 覆盖非空目录，

### F-26　快照装失败仍上报成功，导致静默发散 【已修复】

**严重度：高（集群静默发散）**

`RaftStateMachine::ApplySnapshot()` 返回 `void`，因此
`HandleInstallSnapshot()` 无法得知状态机是否真的装上了，却无条件回
`success = true`。链路上：

1. follower 装快照失败（磁盘满 / 负载损坏），但日志被照常截断、
   `commit_index_`/`last_applied_` 照常推进
2. follower 回「成功」
3. leader 于是推进该节点的 `next_index_`/`match_index_`，并把它**计入多数派**
4. leader 可以据此提交后续条目，而这个节点一条都没应用

**修复**：

- `RaftStateMachine::ApplySnapshot()` 改为返回 `Status`
- `HandleInstallSnapshot()` 在**触碰日志与索引之前**应用快照；失败则原样返回
  `success = false`，节点保持原状。保留旧日志很重要——leader 仍可以靠增量条目
  把它追上来；若先截断再失败，该节点将彻底无法到达任何已提交状态

**测试**：`raft_test: TestFailedInstallIsReportedAndNonDestructive` —— 让状态机
故意返回 `Corruption`，断言回 `success=false`，且 `log_count`/`commit_index`/
`last_applied`/`last_snapshot_index`/`snapshot_data` 全部原封不动；随后让状态机
恢复正常，重试必须成功。

### F-27　快照 payload 形态与实现 【已完成】

`RaftCommandAdapter::TakeSnapshot()` 此前返回空串、`ApplySnapshot()` 是空实现，
所以集群行为至今是「不压缩」。本次补齐，并顺势把 payload 从「整个 DB 目录」
改成**完整 key 空间镜像**：

- 目录不是自描述的，而且要恢复它就得在运行中的 Server 底下换掉 DB 对象
  （99 个 handler 持有裸 `DB*`）
- 完整镜像走 `DB::Clear()` + 批量写即可，不需要任何手术
- 镜像是完整的，所以装到一个从未见过前面那些条目的 follower 上，
  得到的就是 leader 的状态

镜像里**故意不含 range 墓碑**：`Clear()` 之后已经没有任何东西需要被它遮蔽，
而镜像本身已经省掉了它删掉的每一个 key。TTL 元数据会随行——它就存在 DB 里
（`ttl_key`），属于 key 空间的一部分。

格式与编解码抽到 `include/lightkv/state_snapshot.h` + `src/state_snapshot.cpp`
而不是留在 `main()` 里，这样测试跑的是与线上**同一份代码**，而不是它的拷贝。

解码**先完整校验再落地**：magic、版本、每个长度前缀、尾部无多余字节，
以及「声明的条目数不可能塞进剩余字节」这一条（否则一个损坏的 count 能驱动
一次巨额分配）。任何一项不过就整体拒绝，节点继续用现有状态服务。

> 这里踩过一个坑值得记下来：最初用「批大小 + 循环」实现分页，但
> **`DB::Scan` 没有游标**——每次调用都从 `SeekToFirst()` 开始且**追加**到传入的
> vector。于是循环会反复吐出同一段前缀；当 key 总数恰好是批大小的整数倍时
> **永不终止**。改为单次不限量扫描（镜像本来就要整体驻留内存，分页省不下什么）。

**测试**（`cluster_test` 73 -> 90 项）：
- 镜像往返：leader 镜像装到一个带有**不同状态**的 follower 上，断言 follower
  采用了 leader 的 key、丢掉了自己的陈旧 key、逐 key 与 leader 完全一致
- 截断 / 垃圾负载必须被拒绝，且**节点状态不受影响**（仍能读到原有 key）
- 2 万个 key 的库：断言镜像里每个 key 恰好出现一次、首尾 key 都在
  —— 专门盯上面那个分页 bug

**遗留**：`RaftServer::SendInstallSnapshot` 仍是单次全量发送，`data_len` 是
`uint32_t` 且无流控，大快照会一次性打满内存并阻塞。分块传输需要新增 RPC 类型，
建议单独立项。

### F-25　`DB` 缺 `Clear()`，FLUSHDB 无实现 【已修复】

`docs` 此前把「`DB` 没有 `Clear()`」列为 Phase 2.3 的前置阻塞项。审查时还发现
更直接的问题：**`FLUSHDB` / `FLUSHALL` 被列进了 `is_mutating_command` 和主从复制的
`write_cmds`，却根本没有注册 handler**——客户端只会收到 unknown command，
而这条命令对外宣称是集群可复制的。

**修复**：

- `DB` 增加 `virtual Status Clear() = 0`，`DBImpl::Clear()` 实现：
  - 先取 `rw_mutex_` **独占**锁——它是 `WriteLevel0Table` 与各压缩路径持锁期间
    增删文件的依据，拿到之后 `levels_` 不会再被回填。本文件内不存在
    「先 `rw_mutex_` 后 `mutex_`」的路径，因此这个加锁顺序不会与既有的
    `FlushMemTable`/`WriteLevel0Table` 顺序构成反转
  - 若有在途刷盘则等待其落地。刷盘失败必须报错——那些写已经对调用方确认过，
    不能跟着 memtable 一起被丢掉
  - 清空 memtable / imm / levels / pending_delete，重置 manifest、
    `last_seq_`、`next_file_id_`、`flushed_seq_`、活跃快照
  - 轮换 WAL（否则下次打开会把已丢弃的数据重放回来）、重建 `VLogManager`
    并删除旧 `vlog-*.log`
  - **先写空 manifest 再删文件**：若这一步失败，旧文件集合仍在磁盘上有描述，
    可以安全退出而没有删掉 manifest 仍引用的数据
  - 有活跃迭代器时把文件挂进 `pending_delete_` 延后删除——Windows 拒绝删除

- `server.cpp` 注册 `handle_flushdb`，`FLUSHDB` / `FLUSHALL` 共用。
  本store 没有 `SELECT`、也没有多 database，两者语义相同
- SDK 补 `Client::FlushDB()` / `FlushAll()` / `Client::Del()`
- 集群模式下 FLUSHDB 仍走 `is_raft_replicated_command` 的**拒绝**分支。
  `Clear()` 对 KV 状态而言是确定的，但放大复制面需要单独审计确定性与

### F-28　SCAN 游标 / RANDOMKEY / SDK 嵌套数组 【已修复】

**一、SCAN 游标**

原实现有三处独立缺陷：

1. **游标是重扫数组的下标**。两次调用之间只要有写入，数组就整体移位，客户端
   静默漏 key 或重复拿到。每一页的代价还是一次全库扫描。
2. **`next_cursor = cursor + matched.size()` 根本推不动**。循环内部会跳过内部
   key 和不匹配 MATCH 的 key，所以位移量对不上；当 MATCH 一个都匹配不上时
   `matched.size() == 0`，游标原地不动，**客户端死循环**。
3. **100000 的硬上限**。超过这个数的 key 永远扫不到，而 SCAN 会「正常」结束。

改为游标 = **上次返回的最后一个 key**。它不能是数字下标，也不能直接就是 key
本身——key 是任意字节串，`"hello"` 没法按数字解析，而 `"5"` 与 `"05"` 会碰撞。
最终用 **hex 编码**：任何 key 都能往返，且不会与 `"0"` 这个起始哨兵相撞。
每次调用只 `Seek(cursor_key)` 之后向前迭代，代价与页大小成正比。

顺带修掉 `snapshot_seq = 0` 被原样传进 `DBImpl::Iterator` 的问题——
`DBImpl::Scan` 会先把 0 替换成实时 `last_seq_`，而 `SkipInvisible(0)` 会把
**每一条**都当成「比快照新」而跳过。

只有确实还有后续时才返回非零游标：否则每页都会多一次无意义的往返，
而返回 0 又会让「整页被 MATCH 过滤掉」看起来像扫描结束。

**二、RANDOMKEY**

原实现只扫前 1000 个 key 再随机选，所以在更大的库上 RANDOMKEY **只能返回第一页
里的 key**。改为统计全部可见 key 后在 `[0, N)` 上均匀取样。

**三、C++ SDK 遇到嵌套数组会永久阻塞（本次排障时发现）**

`Client::send_command()` 的数组解析是平铺循环，遇到嵌套数组时
`else if (response[pos] == '*') { break; }` ——「skip for simplicity」。
于是 `parsed` 永远追不上 `count`，客户端一直 `recv()` 等一个永远不会到来的
后续包。SCAN 的 `*2\r\n<cursor>\r\n*7\r\n...` 正是第一个嵌套数组回复，
HGETALL 一类命令同理。

改用递归的 `resp_frame_length()` 走完整个 RESP 帧（带深度上限防畸形输入），
任何一处不完整就继续读，超过 16MB 则放弃而不是无限等。

> 这一条是写 SCAN 测试时卡住才挖出来的：服务端已经正确返回，客户端却在死等。
> 定位方式是给 handler 打探针逐步确认边界——如果没先确认「服务端已返回」，
> 很容易误以为是 SCAN 逻辑死循环。

**测试**：`server_test` 新增 SCAN 往返用例——用 COUNT 7 走完整个 key 空间，
断言 53 个 key **各出现且仅出现一次**（含非数字 key `zzz_last_key` 与
DELRANGE 后幸存的 `c`/`d`，以及已删除的 `a`/`b` 不复活）；`MATCH` 全不匹配时
游标必须归零（否则客户端死循环）；`MATCH scan_1*` 精确返回
`scan_1` + `scan_10..19` 共 11 个；非法游标返回 `ERR invalid cursor` 而不是静默从头开始。

### F-30　Pub/Sub 消息从未送达，却一直报成功 【已修复】

F-29 记录的「Pub/Sub 投递全断」根因不止一层，逐层挖出三个独立缺陷。

**一、handler 拿不到自己的连接 fd**

`CommandHandler` 签名是 `std::string(const std::vector<std::string>&)`，没有
`Connection&`。`handle_subscribe` / `handle_psubscribe` / `handle_watch` 因此
全部写死 `make_conn_notifier(/*fd=*/-1)`，而回调里 `connections_.find(-1)`
**必然失败**——消息永远送不到任何客户端，`PUBLISH` 却照常返回非零。

不改签名（那要动 ~99 处注册），改为在派发处设置 `thread_local int g_current_fd`：
`handle_tcp_command()` 与 worker 池里的 lambda 在调用 handler 前后各置一次。

**二、跨连接投递走了永远不会被 flush 的队列**

回调原先直接改 `it->second.send_buf` 并调 `mod_event()`——但 `PUBLISH` 跑在
**worker 线程**上，而 `connections_` 由事件循环独占访问，这本身就是数据竞争。

改走既有的线程安全路径 `on_worker_complete(fd, resp)`（持 `conn_mutex_` 压入
`pending_responses`）。但这条路径当时**根本不会被消费**：

```cpp
void drain_responses() {
    if (!pool_) return;     // ← 默认 worker_threads = 0
```

默认配置没有 worker 池，于是 `drain_responses()` 每次循环都直接返回，
`pending_responses` 里的东西永远躺着。去掉这个门禁——每次循环多做的只是每连接
一次 `empty()` 检查，开销可忽略。**这条此前是潜伏的**：只要将来有任何一个后台
线程用 `on_worker_complete` 投递，回复就会静默丢失。

**三、`UNSUBSCRIBE` 清空的是所有人的订阅**

`handle_unsubscribe` / `handle_punsubscribe` / `handle_unwatch` 一律调
`WatchHub::Clear()`，A 的订阅会被 B 的 `UNWATCH` 一起清掉。
`WatchHub::Unsubscribe(id)` 早已实现却无任何调用点。

新增 `conn_watchers_`（fd → watcher_id 列表，独立互斥量，**不放在 `Connection`
里**——handler 跑在 worker 线程而 `Connection` 生命周期归事件循环管），
退订只摘自己那一份。

**四、`PUBLISH` 返回全局 watcher 数**

向一个没人订阅的频道发布，也会返回「有 N 个接收者」。`WatchHub::Notify()` 改为
返回**实际投递数**。

**五、频道名写死为 `"message"`**

回调里 `std::string channel = "message";  // 简化：统一用 message 频道名`，
注释还自承。频道名其实就编码在 WatchHub 的 key 里（`__channel__:<name>`），
`channel_from_key()` 还原即可。

**测试**：`server_test` 新增 Pub/Sub 用例——开两条真实连接，断言
`SUBSCRIBE` 后 `PUBLISH` 返回 `:1`、无人订阅的频道返回 `:0`、
**订阅方确实在自己的 socket 上收到 `message/news/hello`**、
B 的 `UNSUBSCRIBE` 不影响 A 的订阅、A 退订后回到 `:0`。

> 排障过程本身值得记一笔：症状是「订阅方收不到消息」，但服务端 `PUBLISH`
> 明确返回了 1，说明回调**确实被调用过**。逐层加探针后定位到
> `drain_responses()` 一次都没执行——若不是先确认「回调已触发」，
> 很容易误以为是订阅匹配有问题而往 `WatchHub` 里挖。

### F-31　主从复制：master 侧全是死代码，且 RDB 生成会卡死进程 【部分修复】

对主从复制做了完整调研。结论是：**master 侧骨架齐全但一端未接，slave 侧基本没写**。
本次修掉 master 侧的所有低成本缺陷，并把无法诚实支持的 `REPLICAOF` 改成明确报错。

**一、`generate_rdb_snapshot()` 会无限循环直到 OOM（严重）**

```cpp
const int batch_size = 100;
while (true) {
    results.clear();
    Status s = db_->Scan(ro, "", batch_size, &results);
    ...
    if (static_cast<int>(results.size()) < batch_size) break;
}
```

这正是 F-27 记录过的 **`DB::Scan` 没有游标**问题：每次调用都从
`SeekToFirst()` 重新开始。key 数一旦 ≥ 100，循环就会**反复吐出同一批前 100 个
key 并不断追加**，直到把内存吃光——而且它跑在**事件循环线程**上，
一次 PSYNC 就能把整个 master 卡住。

改为单次 `Scan(ro, "", 0x7FFFFFFF, ...)`。

**二、`AddSlave` / `RemoveSlave` / `UpdateSlaveAck` 零调用点**

`slaves_` 因此恒空 → `SlaveCount()` 恒 0 → `feed_replication()` 第一行
`if (SlaveCount() == 0) return;` 永远命中 → backlog 永远不写、`repl_offset_`
永远是 0、`INFO` 里的复制统计全是 0。整条推流链路是死代码。

`handle_psync` 硬编码 `slave_fd = -1`（注释自承 "need to track it"），
使 `HandlePSYNC` 内部所有 `s.fd == slave_fd` 循环都落空。改用 F-30 引入的
`g_current_fd`，并在 PSYNC 时 `AddSlave`、连接关闭时 `RemoveSlave`。
`AddSlave` 改为幂等，否则重连会重复登记、把每段 backlog 发两遍。

**三、只读的「唯一线程安全投递通道」是空的**

`execute_replication_command()`、RDB 解析、slave 重连循环、握手状态机
**全部不存在**——`master_repl_id_` / `master_repl_offset_` / `repl_recv_buf_`
三个字段从未被写入过任何值。

真正把 slave 接上去需要新写的东西（已列入待办）：出站非阻塞 connect 与注册、
复制状态机与指数退避重连、`LKVDB01` RDB 解析器与加载、增量命令流解析、
`REPLCONF ACK` 周期上报、以及 Windows IOCP 侧的出站连接支持。
这是一次独立的大工程，不适合夹在缺陷修复里顺手做。

**四、`REPLICAOF` 不再假装成功**

原实现设完 `is_slave_` / `readonly` / `master_host` / `master_port` 就
`return resp_ok()`，末尾是 `// TODO: Connect to new master`。运维会认为节点
已在复制，`INFO` 会宣称 `role:slave`，而它**永远不会收到任何一次写入**。
现在直接返回明确错误，并指向可用替代方案（`--cluster` Raft）。

**五、`REPLCONF` 丢参 → 真正记录**

`capa` / `listening-port` / `ack` / `ack-time` 全部被 `(void)` 丢弃，
`UpdateSlaveAck` 因此零调用、`ack_offset` 永远是 0。现在：
`ack` → `UpdateSlaveAck`（非数字 offset 返回错误而非静默吞掉），
其余记录到受互斥保护的 slave 元数据里。

**六、CONTINUE 退化成全量**

`process_tcp` 里只要是 PSYNC 就无条件 `send_rdb_to_slave()`，而
`HandlePSYNC` 返回的 `FULLRESYNC` / `CONTINUE` 关键字在
`handle_psync` 内部被解析掉就丢弃了。结果：**slave 已经追平时反而还要全量 dump**，
正好抵消了部分重同步的意义。改为用 `psync_full_sync_` 集合标记，
只有 FULLRESYNC 才触发 dump。

**七、只读副本在多线程模式下可写（高）**

`opts_.readonly` 的检查只存在于 `handle_tcp_command`（单线程路径）。
`dispatch_to_worker` 里查了 AUTH、HELLO 和 Raft 闸门，**唯独没查 readonly**——
`--worker-threads > 0` 时只读副本可以接受任意写入。抽出 `readonly_guard()`
供两条路径共用。

**测试**：`server_test` 新增复制用例——先写入 **250 个 key**（确保越过 100 这个
阈值，否则测不到 RDB 分页死循环），断言 `DBSIZE >= 100`；`REPLICAOF host port`
必须返回 `-ERR`；`REPLCONF` 三个参数返回 `+OK` 且非数字 ack 返回 `-ERR`；
`PSYNC ? -1` 能正常返回 bulk 回复且**不挂起**（旧实现在这里会无限追加直到
OOM）；`INFO replication` 含 `connected_slaves:`。实测生成 11710 字节 RDB
（250 key × ~47 字节）并正常结束。

**仍待处理**：第三节列出的 slave 侧全部内容；`master_auth` 与
`repl_ping_interval_ms` 两个选项仍是死配置；RDB 分支 `return` 导致
`send_buf` 不 flush 的发送顺序问题（Windows 上 `mod_event` 是空操作，
RDB 传输与 backlog 推送在 Windows 上都不通）。

### 注意事项

1. **§1.1 的环境陷阱会让验证结果失真**。务必在 `%TEMP%` 或 CI 干净环境中运行测试，
   不要直接用 `build/` 目录下的二进制下结论。`run_full_test.ps1` 已内置该规避。
2. **测试之间共享固定端口**（16379 / 16382 / 16383）与共享临时目录 `C:\lightkv_tmp`。
   残留的服务进程会让后续测试**连到错误的服务**并报出无关失败。
   并行跑多个测试二进制是不可靠的。
3. **Phase 1b 已改变磁盘格式**（footer magic `LIGHTKV2`）。旧数据目录会被明确拒绝，升级需重建。
4. **F-3 的修复是近似的**：`file_id` 反映的是 flush 顺序而非版本顺序。
   在「同一文件内多版本」的场景下依赖跳表的 LIFO 契约（见 §四 隐性契约警告）。
5. **F-10 修复后 Raft 集群不再压缩日志**。这是「正确但低效」的取舍，
   在 Phase 2.3 补齐真实快照之前，leader 的日志会持续增长。
6. **Raft 此前从未被端到端验证过**。F-14/F-15/F-16 都是新增 `cluster_test`
   时立刻暴露的，说明「文档标注已实现」与「实际可用」之间存在系统性落差。
   后续改动 Raft 时应先确保 `cluster_test` 与 `raft_test` 持续通过。
7. **`DELRANGE` 的两个坑是叠加的**。F-18 修好了返回值，F-19 才修好语义本身——
   只改计数会让 `DeleteRange` 对着一个被旧墓碑遮蔽的世界报数（测试里表现为
   「counted 0, expected 5」）。改任何 range tombstone 相关代码前，先确认
   `version_seq` 比较没有被去重。
8. **`Client::DeleteRange` 返回 bool，不返回数量**。需要真实计数请直接用
   `send_command` / `DB::DeleteRange(..., &n)`。
9. **`log_[i]` 持有的是绝对索引 `log_base_ + i`**。任何直接按位置下标访问
   `log_` 的新代码都必须先过 `LogPos()`，否则压缩后会读到错位的条目
   （F-22 就是这么发生的）。
10. **Raft 的持久化路径从 2026-10 起才被测试覆盖**。F-20/F-21/F-22/F-23 全都
    藏在「没有测试重启过节点」这个盲区里。改 Raft 持久化或日志结构时，
    必须让 `raft_test` 覆盖重启路径。
11. **`DBImpl::Backup()` 从 2026-10 起才被测试覆盖**（F-24）。它此前在生产里
    也没有真正的调用方——`/backup` HTTP 接口只返回一句写死的 JSON。
    写任何新的持久化/导出路径时，先想清楚：**产物能否被独立打开**、
    **并发写入/压缩下是否仍然自洽**、**失败时是否留下半成品**。
12. **命令名出现在白名单里不等于它有实现**。`FLUSHDB` 同时出现在
    `is_mutating_command` 和主从 `write_cmds` 里，却从没注册 handler（F-25）；
    `SendSnapshotToFollower()` 只声明没定义；`handle_backup()` 返回写死的 JSON。
    改白名单时顺手确认 `cmd_table_` 里有对应条目。
13. **`DB::Scan` 没有游标**。它每次都从 `SeekToFirst()` 开始并**追加**到传入的
    vector，因此不能用「批大小 + 循环」实现分页：会反复吐出同一段前缀，且当
    key 总数恰好是批大小整数倍时永不终止（F-27）。要按需遍历就用
    `DBImpl::Iterator`。
14. **`ReadOptions::snapshot_seq = 0` 是「最新」，不是「seq 0」**。直接把它传给
    `DBImpl::Iterator` 会让 `SkipInvisible(0)` 把每一条都当成比快照新而跳过。
    `DBImpl::Scan` 内部会替换成实时 `last_seq_`，绕过它就要自己替换（F-28）。
15. **服务端返回正确 ≠ 客户端读得到**。F-28 里客户端因为解析器不支持嵌套数组
    而永久阻塞。排障时先给 handler 打探针确认边界，能省掉大量猜测。
16. **注释会骗人，测试不会**。F-29 里的 `// Approximate by scanning` 描述了一次
    从未写出来的扫描，`// Deterministic: return middle element` 把一个假随机
    包装成了「有意为之的设计」。看到这类注释先按「它在替缺失的实现辩解」处理。
17. **「看起来线程安全」和「线程安全」是两回事**。F-30 里
    `drain_responses()` 开头一句 `if (!pool_) return;`，而默认 `worker_threads = 0`
    —— 于是 `on_worker_complete()` 这条唯一的线程安全投递路径**一次都不会被消费**。
    加一个「看起来对」的锁/队列很容易，忘了它下游没人 drain 就很难发现。
18. **症状能缩小范围，别只盯着最可疑的那层**。F-30 里订阅方收不到消息，
    最自然的猜测是 `WatchHub` 的匹配逻辑有问题；但 `PUBLISH` 返回了 1，
    说明回调已被调用，范围立刻缩到「回调内部」再缩到「队列没人消费」。
